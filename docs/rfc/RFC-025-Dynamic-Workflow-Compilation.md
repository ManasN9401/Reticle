# RFC-025 — Dynamic Workflow Compilation

Status: Draft
Version: 1.0.0
Author: HyperParallel Core
Last Updated: 2026-08-04

---

## 1. Purpose
This document defines the "Zero-Boilerplate Orchestrator" capability, detailing how HyperParallel will transition from requiring bespoke Go scripts to accepting natural language prompts that dynamically compile into executed workflows.

## 2. Motivation
In early iterations, developers had to write a `main.go` file to manually bootstrap the `GraphEngine`, configure the `TaskDispatcher`, and point to hardcoded YAML files. To make the orchestrator a truly ubiquitous CLI, it must abstract this boilerplate away.

## 3. Scope
This RFC covers:
- The top-level `Compiler Agent`.
- The mechanism of translating Natural Language (NL) to Directed Acyclic Graphs (DAG).
- In-memory YAML generation and execution injection.
- The Universal CLI interface.

## 4. Philosophy
The orchestrator should behave as a universal operating system for intelligence. Just as a user does not compile a C program to run a shell command, a user should not compile a Go binary to execute an AI workflow.

## 5. Principles
- **Zero-Boilerplate**: The user provides a goal; the system provisions the workers.
- **In-Memory Compilation**: Intermediate YAML structures generated by the Compiler Agent should be held in memory, leaving the user's filesystem clean unless requested otherwise.
- **Transparency**: The user must be able to view and modify the dynamically generated DAG via the Dashboard UI before or during execution.

## 6. Architectural Laws
1. A new `Compiler Agent` must sit between the user's CLI prompt and the `GraphEngine`.
2. The `Compiler Agent` must output valid HyperParallel `Agent Definition Schema` and `Workflow Definition Schema` structures.
3. The orchestrator must parse the Compiler's output and dynamically instantiate the `GraphEngine` in memory.
4. The universal entrypoint will be standard `hyperparallel` commands (e.g., `hyperparallel run -prompt "..."`).

## 7. Rationale
By leveraging a meta-agent (the Compiler) to design the workflow, we achieve maximum flexibility. The orchestrator engine itself doesn't need to understand natural language—it only needs to execute the generated DAG. This maintains the strict isolation boundaries defined in RFC-003.

## 8. Trade-offs
- Relying on an LLM to generate the initial graph introduces a latency hit before the actual work can begin.
- The Compiler Agent may hallucinate invalid topologies (e.g., circular dependencies), requiring strict validation loops in the orchestrator before execution begins.

## 9. Future Considerations
- Caching compiled graphs: if a user prompts "Write a book about Space" and later prompts "Write a book about Oceans", the orchestrator could bypass the Compiler Agent and reuse the previously generated "Book Creator" topology, simply swapping the input prompt.
